# Image storage with Spring MVC

This is the blocking Kotlin and Spring Boot version of a small image storage API. A signed-in user can upload an image, keep it private or share it by URL, and delete it later. A future WebFlux version can use the same HTTP contract and permission rules so we can compare how the two stacks handle the same work.

## Initial model

- **Image ID** — a UUID generated by the API. The API derives the storage key from this ID and controls the image's visibility.
- **Visibility** — `PRIVATE` or `PUBLIC`, chosen on upload. Anyone with the public image's API URL can request a download. Only the uploader can download a private image or delete an image of either visibility.
- **Upload settings** — start with JPEG and PNG and a proposed maximum of 5 MiB. The client declares the content type and size when requesting an upload URL. The API checks the uploaded bytes before making the image available.
- **Storage** — keep image bytes and basic metadata in the local S3-compatible store, with a private bucket for both visibilities. OpenFGA stores the uploader's `owner` relationship to the image. This version needs no separate application database.

## Four endpoints to start with

| Endpoint | Who can use it | What it does |
| --- | --- | --- |
| `POST /images/uploads` | Signed-in user | Accepts visibility, content type, and size. Allocates an image ID, records the owner, and returns a short-lived presigned `PUT` URL for a staging object. |
| `POST /images/{id}/complete` | Owner | Checks the uploaded object and makes the validated image available. |
| `GET /images/{id}/download` | Anyone for public images, owner for private images | Returns a short-lived presigned `GET` URL for a completed image. |
| `DELETE /images/{id}` | Owner | Deletes the image through the API. |

Public and private downloads can share a route. The API looks up the image's visibility before deciding whether to require authentication and an OpenFGA check. If we give public and private downloads separate routes, the same flow would have five endpoints. Keeping a completion step gives us a place to validate the actual upload after the browser sends its bytes directly to storage.

## Authentication, permissions, and file transfer

The auth service issues access tokens. The image API validates the JWT signature, issuer, expiry, and audience for this API. It uses the token's `sub` as the uploader ID. OpenFGA answers questions such as whether `user:<sub>` can delete `image:<id>`. The first model can derive `can_download_private`, `can_complete`, and `can_delete` from the image's `owner` relationship. [OpenFGA modeling guide](https://openfga.dev/docs/modeling/getting-started)

The browser transfers the bytes directly to the local S3-compatible store. The API authorizes URL issuance, and storage checks the URL's signature and expiry when it receives the request. Someone who receives a private download URL can use it while it is valid, so keep its expiry short. Give upload URLs a staging key separate from the published key so retrying a `PUT` cannot overwrite the completed image. [S3 presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

## Experiments for later

- **Retry or abandon an upload.** Make completion safe to retry and clean up expired staging objects. This gives us a small example of coordinating state across S3 and OpenFGA.
- **Compare MVC and WebFlux with the same requests.** Start with blocking clients in MVC, then try nonblocking I/O in WebFlux. Compare concurrent requests that wait on storage and OpenFGA. The actual file transfers bypass both APIs, so the comparison is about how they handle the work that remains.

## Implementation plan

1. [ ] **Initialize the Spring MVC service.** Add the Kotlin and Spring Boot project to the root Gradle build. Sketch the controller, request and response types, service, and error handling around the four routes above. Keep the HTTP layer separate from the storage and permission calls so we can reuse the same API contract in WebFlux later.
2. [ ] **Connect S3 and OpenFGA.** Configure the S3 client and presigner for the local store, using a browser-reachable endpoint in signed URLs. Connect to OpenFGA, define the initial owner-only model, and document how to load it and configure the store and model IDs. Wire the image API as a Spring Security resource server and configure the expected token issuer and audience with the auth service.
3. [ ] **Implement the four image routes.** Record the uploader as owner when issuing a staging upload URL. Validate the uploaded bytes on completion before publishing the image. Issue download URLs for public images or for owners of private images. Check ownership before deleting either kind of image. Cover anonymous downloads, owner access, and denials for a signed-in user who does not own the image.
4. [ ] **Add viewer sharing as a separate change.** Extend the OpenFGA model with `viewer` and change `can_download_private` to `owner or viewer`. Add owner-only endpoints to grant and revoke access, using the recipient's user UUID. Cover the cases where a viewer can download but cannot delete or share, and where revocation blocks new download URLs. Previously issued URLs can still work until they expire.
