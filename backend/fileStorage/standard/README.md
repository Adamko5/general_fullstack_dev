# Image storage with Spring MVC

This is the blocking Kotlin and Spring Boot version of a small image storage API. A signed-in user can upload an image, keep it private or share it by URL, and delete it later. A future WebFlux version can use the same HTTP contract and permission rules so we can compare how the two stacks handle the same work.

Run Gradle tasks from the repository root with `./gradlew -p backend/fileStorage/standard <task>` or `gradlew.bat -p backend/fileStorage/standard <task>` on Windows.

## Initial model

- **Image ID** — a UUID generated by the API. The API derives the storage key from this ID and controls the image's visibility.
- **Visibility** — `PRIVATE` or `PUBLIC`, chosen on upload. Anyone with the public image's API URL can request a download. Only the uploader can download a private image or delete an image of either visibility.
- **Upload settings** — start with JPEG and PNG, a maximum of 5 MiB, and a maximum decoded size of 16 megapixels to bound validation memory. The client declares the content type and size when requesting an upload URL. The API checks the uploaded image before making it available.
- **Storage** — keep image bytes and basic metadata in the local S3-compatible store, with a private bucket for both visibilities. Staging and published objects carry their owner and visibility as S3 metadata. OpenFGA stores the uploader's `owner` relationship to the image. This version needs no separate application database.

## Four endpoints to start with

| Endpoint | Who can use it | What it does |
| --- | --- | --- |
| `POST /images/uploads` | Signed-in user | Accepts visibility, content type, and size. Allocates an image ID, records the owner, and returns a short-lived presigned `PUT` URL for a staging object. |
| `POST /images/{id}/complete` | Owner | Checks the uploaded object and makes the validated image available. |
| `GET /images/{id}/download` | Anyone for public images, owner for private images | Returns a short-lived presigned `GET` URL for a completed image. |
| `DELETE /images/{id}` | Owner | Deletes the image through the API. |

Public and private downloads can share a route. The API looks up the image's visibility before deciding whether to require authentication and an OpenFGA check. If we give public and private downloads separate routes, the same flow would have five endpoints. Keeping a completion step gives us a place to validate the actual upload after the browser sends its bytes directly to storage.

## Authentication, permissions, and file transfer

The frontend requests `http://localhost:8083` as its OAuth `resource`. The auth service checks that URI against the requesting client's `allowedResourceUris` and places the approved URI in the access token's `aud`. The image API validates the JWT signature using the issuer's JWKS, plus the issuer, expiry, and its own audience URI. It uses the token's `sub` as the uploader ID. OpenFGA answers questions such as whether `user:<sub>` can delete `image:<id>`. The initial model derives `can_download_private`, `can_complete`, and `can_delete` from the image's `owner` relationship. [OpenFGA modeling guide](https://openfga.dev/docs/modeling/getting-started)

The browser transfers the bytes directly to the local S3-compatible store. The API authorizes URL issuance, and storage checks the URL's signature and expiry when it receives the request. Someone who receives a private download URL can use it while it is valid, so keep its expiry short. Give upload URLs a staging key separate from the published key so retrying a `PUT` cannot overwrite the completed image. [S3 presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

## Local integration settings

The S3 configuration reads `S3_ENDPOINT_URL`, `S3_PRESIGNED_URL_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, and `S3_SECRET_KEY`. Local defaults use `http://localhost:8333`, region `us-east-1`, bucket `image-storage`, and the development credentials from the support Compose file. At startup the service creates the bucket if it is missing and sets its browser CORS rules for `CORS_ALLOWED_ORIGINS`. When the service runs directly on the host, both endpoints can use `http://localhost:8333`. If the service runs in Compose later, `S3_ENDPOINT_URL` must use the service name, such as `http://s3:8333`, while `S3_PRESIGNED_URL_ENDPOINT` must remain reachable by the browser, such as `http://localhost:8333`. The client and presigner use path-style addressing for the local S3-compatible service.

OpenFGA needs a store and an authorization model. Start the support services from `auth/`, install the [OpenFGA CLI](https://github.com/openfga/cli), then run these commands from `backend/fileStorage/standard` to create a store from the model file:

```powershell
$store = fga store create --api-url http://localhost:8082 --name image-storage --model .\src\main\resources\openfga\image-storage.fga | ConvertFrom-Json
$env:OPENFGA_STORE_ID = $store.store.id
$env:OPENFGA_AUTHORIZATION_MODEL_ID = $store.model.authorization_model_id
```

Set `OPENFGA_API_URL`, `OPENFGA_STORE_ID`, and `OPENFGA_AUTHORIZATION_MODEL_ID` in the service's run configuration. The store and model IDs come from the CLI response. The service uses the Java SDK client with those IDs. The API allows anonymous requests through the download route so public images can be served. All other routes require a bearer token. API CORS allows the local frontend origin from `CORS_ALLOWED_ORIGINS`. S3 bucket CORS allows browser `PUT`, `GET`, and `HEAD` requests from the same configured origin.

The auth service's local issuer is `http://localhost:8080`. The image API's `AUTH_OIDC_AUDIENCE` defaults to `http://localhost:8083`, which must match the URI requested by the frontend and allowed for its client in `auth/oidc-clients.local.json`.

## Experiments for later

- **Retry or abandon an upload.** An abandoned upload currently leaves its owner tuple in OpenFGA, and a lost completion response can make a retry report a missing staging object. Make completion safe to retry and clean up expired staging objects. This gives us a small example of coordinating state across S3 and OpenFGA.
- **Compare MVC and WebFlux with the same requests.** Start with blocking clients in MVC, then try nonblocking I/O in WebFlux. Compare concurrent requests that wait on storage and OpenFGA. The actual file transfers bypass both APIs, so the comparison is about how they handle the work that remains.

The service validates actual PNG/JPEG decoding, the declared byte length, a 5 MiB file limit, and a 16 megapixel decoded-image limit. Unit tests cover public and private downloads, owner and non-owner deletion, upload authorization, and completion validation.
4. [x] **Add viewer sharing as a separate change.** Extend the OpenFGA model with `viewer` and change `can_download_private` to `owner or viewer`. Add owner-only endpoints to grant and revoke access, using the recipient's user UUID. Cover the cases where a viewer can download but cannot delete or share, and where revocation blocks new download URLs. Previously issued URLs can still work until they expire.
